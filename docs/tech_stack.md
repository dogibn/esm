# Tech stack

Framework choices, conventions, and patterns. The stack is intentionally boring: Next.js + TypeScript + Supabase + Drizzle + shadcn/ui. Each choice is justified by *this* project's constraints (internal tool, 5 users, ~1000 students, single tenant), not by what other companies do at scale.

For *what* the system models, see `domain_model.md`. For DB shapes, see `schema.md`.

---

## 1. Framework & runtime

- **Next.js 15+ (App Router).** File-system routing, API route handlers, SSR for the tracking view, single-repo deployment.
- **TypeScript** — strict mode (`"strict": true`). Non-negotiable.
- **Node.js 20 LTS.**
- **Package manager:** pnpm. Lockfile committed.

---

## 2. Database & ORM

- **PostgreSQL via Supabase**, region `ap-northeast-1` (Tokyo).
- **Drizzle ORM** with the `postgres-js` driver. Schema in TypeScript at `db/schema.ts`. Migrations generated by `drizzle-kit` into `drizzle/`.

**Conventions:**
- Drizzle client is instantiated **once** in `db/index.ts` (singleton via `globalThis` to survive hot-reload). Import `db` from there everywhere.
- **Connection: pooled** (Supabase pgBouncer on port 6543) **with `prepare: false`** — pgBouncer transaction mode doesn't support prepared statements. The direct connection (port 5432) is used only by `drizzle-kit` for migrations.
- Migration workflow:
  1. Edit `db/schema.ts`
  2. `pnpm drizzle-kit generate` produces SQL under `drizzle/`
  3. Review the generated SQL
  4. `pnpm drizzle-kit migrate` applies it
- Generated migrations are committed to git. Never edit a migration after it's been applied — generate a new one instead.
- **DB access only happens server-side.** Frontend talks to `app/api/*`, never imports `db`.
- For each table, re-export the row and insert types from `db/schema.ts`:
  ```ts
  export type Student = typeof students.$inferSelect;
  export type NewStudent = typeof students.$inferInsert;
  ```
  These are canonical. Never hand-write a parallel type.

## 3. Backend architecture

API route handlers live under `app/api/<resource>/route.ts`, exporting `GET`, `POST`, etc.

Standard route handler shape:

```ts
export async function GET(req: Request) {
  const user = await requireUser(req);
  const params = listStudentsQuerySchema.parse(parseSearchParams(req));
  const result = await listStudents(user, params);
  return Response.json(result);
}
```

Four responsibilities, in order:
1. **Authenticate** via `requireUser()` / `requireAdmin()`.
2. **Validate** input with a Zod schema.
3. **Delegate** to a service function in `features/<domain>/api.ts`.
4. **Return** typed JSON.

**Conventions:**
- **Validation: Zod, always.** Every body, query param, and route param goes through a Zod schema. No manual `if (typeof x !== ...)` guards.
- **Errors: a single `HttpError`** in `lib/errors.ts` with status codes. A wrapper helper maps thrown `HttpError` to JSON. Service functions throw; route handlers don't catch — the wrapper does.
- **No business logic in route handlers.** They orchestrate. Logic lives in service functions, testable in isolation.
- **No N+1 queries.** Use Drizzle's relational query API (`db.query.X.findMany({ with: ... })`) or explicit JOINs.

## 4. Authentication

- **Supabase Auth** (email/password). Handles password hashing, session tokens, password reset.
- 5 users, all internal. No SSO, no OAuth, no MFA.
- Sessions: HTTP-only cookies via `@supabase/ssr`.
- Two roles: `accountant` (default) and `admin`. Stored on the `users` table.

**Conventions:**
- `requireUser(req)` in `lib/auth.ts` reads the session, returns the User, or throws `HttpError(401)`. First action of every protected route.
- `requireAdmin(req)` for admin-only routes.
- The frontend uses Supabase JS client **only** for auth flows. Never for DB access.

---

## 5. File handling — bank transaction import

- **`xlsx` (SheetJS)** for parsing uploaded Excel files. Battle-tested; handles `.xlsx` and `.xls`.
- Upload pattern: `multipart/form-data` POST to `app/api/imports/upload/route.ts`.
- **Parsing happens server-side.** Never trust the browser to parse and send structured data.
- Parsed rows persist as `bank_transactions` rows before any matching is attempted. Deduplicated by `transaction_id` UNIQUE.
- Matching is a separate service function: takes BankTransaction rows, produces MatchProposal values (in-memory; not persisted).

Parsing and matching live in `features/imports/parsing/` and `features/imports/matching/` as pure functions where possible. Unit tests live next to them.

## 6. Frontend conventions

The pattern below is non-negotiable.

### Primitives in `components/ui/`

Built using **shadcn/ui** (copied into the repo via CLI, owned by us). Behavior from **Radix UI**. Variants via **class-variance-authority (CVA)**. Class composition via **`cn()`** (clsx + tailwind-merge), defined once in `lib/utils.ts`.

Every primitive — Button, Input, Card, Dialog, Table, Tabs, Select, Badge — follows the CVA pattern:

```tsx
const buttonVariants = cva(
  "inline-flex items-center justify-center rounded-md text-sm font-medium transition-colors focus-visible:outline-none disabled:opacity-50 disabled:pointer-events-none",
  {
    variants: {
      variant: {
        default:     "bg-primary text-primary-foreground hover:bg-primary/90",
        outline:     "border border-input bg-background hover:bg-accent",
        ghost:       "hover:bg-accent hover:text-accent-foreground",
        destructive: "bg-destructive text-destructive-foreground hover:bg-destructive/90",
      },
      size: {
        sm: "h-8 px-3",
        md: "h-10 px-4",
        lg: "h-12 px-6",
      },
    },
    defaultVariants: { variant: "default", size: "md" },
  }
);
```

### Design tokens in `app/globals.css`

All colors, radii, and core spacing live as CSS variables. The palette follows
the Figma "Finance Portal" design: blue brand, near-white gray page canvas,
white card surfaces.

```css
:root {
  --primary: 221 83% 53%;       /* blue-600 — brand */
  --background: 220 20% 97%;    /* gray page canvas */
  --card: 0 0% 100%;            /* white surfaces */
  --border: 220 13% 91%;
  --destructive: 0 72% 51%;     /* unpaid / overdue */
  --success: 142 72% 29%;       /* paid */
  --warning: 20 90% 40%;        /* partial */
  --info: 221 83% 53%;          /* category accent (tuition) */
  --violet: 271 81% 48%;        /* category accent (bus) */
  --teal: 175 84% 32%;          /* category accent (clubs/other) */
  --radius: 0.625rem;
}
```

Tailwind v4 reads them via the `@theme inline` block in the same file.
Changing one CSS variable rethemes the entire app. Status colors are
semantic: paid → `success`, partial → `warning`, unpaid/overdue →
`destructive`; the one mapping lives in `features/students/components/StatusBadge.tsx`.

### Hard rules

1. **No raw HTML elements in feature code.** Always `<Button>`, never `<button>`. If a primitive doesn't exist, create it in `components/ui/` first.
2. **No hardcoded colors, radii, spacing, or font sizes.** Always tokens via Tailwind classes.
3. **If a Tailwind string repeats twice, extract a component.**
4. **Page files describe layout, not styling.** A page reads like `<StudentList /> <BalanceSummary /> <ImportButton />`. Tailwind lives one layer down.
5. **Cross-feature imports go through the feature's `index.ts` barrel.** Never deep paths.
6. **No `@apply` in CSS.** Components are the abstraction layer.

## 7. Folder structure

```
app/
  (auth)/login/page.tsx
  (app)/                        # protected routes; layout enforces session
    students/page.tsx           # tracking view
    imports/
      page.tsx                  # upload + recent imports
      [id]/page.tsx             # review proposed matches, confirm
    transactions/page.tsx       # transaction history
    layout.tsx
  api/
    students/route.ts
    imports/
      upload/route.ts
      [id]/confirm/route.ts
    auth/...
  globals.css                   # design tokens
  layout.tsx                    # root layout

components/ui/                  # primitives: Button, Input, Card, Dialog, Table, ...

features/
  students/
    components/                 # StudentTable, BalanceCell, GradeFilter, ...
    api.ts                      # service functions
    schemas.ts                  # Zod schemas
    types.ts
    strings.ts                  # extracted user-facing strings
    index.ts                    # public barrel
  imports/
    components/                 # UploadDropzone, MatchReviewTable, ...
    parsing/                    # SheetJS, pure functions
    matching/                   # matching algorithm, pure functions
    api.ts
    schemas.ts
    types.ts
    strings.ts
    index.ts
  auth/
    components/
    api.ts
    index.ts

lib/
  auth.ts                       # requireUser, requireAdmin
  supabase.ts                   # auth + storage only
  errors.ts                     # HttpError, error handler wrapper
  env.ts                        # validated env vars (Zod)
  utils.ts                      # cn()

db/
  schema.ts                     # Drizzle table definitions
  relations.ts                  # Drizzle relations (for the query API)
  index.ts                      # client singleton
  seed.ts                       # one-time data load

drizzle/                        # generated migrations, committed to git
drizzle.config.ts
```

Group by *what it does*, not *what it is*. A `StudentBalanceTable` lives in `features/students/components/`. Shared primitives — Button, Input, Table — live in `components/ui/` because they're domain-agnostic.

## 8. Forms, tables, validation

- **Forms:** `react-hook-form` with `@hookform/resolvers/zod`. The same Zod schema validates client-side and server-side — never duplicate validation logic.
- **Tables:** `@tanstack/react-table` for the tracking view. Headless logic; rendering uses our `<Table>` primitive.
- **Validation:** Zod is the single validation library. One `schemas.ts` per feature, shared between API and UI.

---

## 9. Localization

- **English only in v1.** No i18n machinery.
- **All user-facing strings are extracted** to `features/<x>/strings.ts`. No string literals in JSX.
- This makes adding Mongolian later mechanical: swap the constants file for an i18n lookup, no JSX changes required.

## 10. Testing

Calibrated for a learning project that needs to ship.

- **Vitest** for unit tests. Highest-value targets:
  - Bank transaction parsing (given a sample Excel, returns expected rows)
  - Matching algorithm (given a transaction, proposes the right matches with the right signals)
  - Zod schemas (round-trip validation of edge cases)
  - Service functions with non-trivial logic (charge calculation, balance computation)
- **Playwright** for one e2e per critical flow:
  - Sign in → tracking view → search/filter
  - Sign in → upload bank file → review → confirm → verify payments recorded
- **Skip:** UI styling tests, simple CRUD endpoints, Drizzle queries themselves.

Tests live next to source: `matching.ts` + `matching.test.ts`.

## 11. Deployment & environment

- **Hosting:** Vercel hobby tier (free).
- **Region:** Tokyo for Vercel functions and Supabase Postgres. ~80–150 ms latency from Ulaanbaatar.
- **Environments:** `development` (local), `preview` (Vercel branch deploys), `production`.
- **Secrets:** Vercel env vars per environment. Local dev uses `.env.local` (gitignored).

**Required env vars:**
```
DATABASE_URL                 # pooled connection (port 6543, pgBouncer)
DIRECT_URL                   # direct connection (port 5432, used by drizzle-kit migrate)
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY    # server-only, never exposed to client
```

A Zod schema in `lib/env.ts` validates env vars at startup and re-exports them typed. If any required var is missing, the app fails to boot — better than mysterious runtime errors.

## 12. Out of scope for v1

Things AI would otherwise re-derive.

- **No RSC mutations, no Server Actions.** Plain API route handlers.
- **No edge runtime.** Node.js runtime everywhere.
- **No WebSockets, no Supabase Realtime.** No live-update features.
- **No i18n machinery.** Strings are extracted but not translated.
- **No multi-tenancy.** Single tenant for ESM.
- **No row-level security (RLS).** Auth at the API layer via `requireUser()` / `requireAdmin()`.
- **No public-facing pages.** Login is the only unauthenticated route.
