# Tech Stack — ESM Payment Tracker

This document is the authoritative source for framework choices, conventions, and patterns for ESM Payment Tracker. It exists primarily as **context for AI-assisted code generation** — the rules below are intended to constrain output across sessions that don't share memory, so that code written in one session is consistent with code written in another.

The stack is intentionally boring: Next.js + TypeScript + Supabase + Drizzle + shadcn/ui. Nothing experimental. Each choice is justified by *this* project's constraints (internal tool, 5 users, ~1000 students, single tenant, single academic year), not by what other companies do at scale.

---

## 1. Framework & Runtime

- **Next.js 15+ (App Router)** — full-stack React framework. Used here for: file-system routing, API route handlers, SSR for the tracking view, single-repo deployment.
- **TypeScript** — strict mode (`"strict": true` in `tsconfig.json`). Non-negotiable.
- **Node.js 20 LTS**.
- **Package manager: pnpm** — lockfile committed.

**Out of scope for v1:** React Server Components for data mutations, Server Actions, edge runtime. Use plain API route handlers under `app/api/`. This keeps the frontend/backend boundary explicit and easy to reason about.

---

## 2. Database & ORM

- **PostgreSQL via Supabase**, region `ap-northeast-1` (Tokyo).
- **Drizzle ORM** with the `postgres-js` driver. Schema defined in TypeScript at `db/schema.ts`. Migrations generated by `drizzle-kit` into `drizzle/`.

**Conventions:**
- The Drizzle client is instantiated **once** in `db/index.ts` (singleton pattern using `globalThis` to survive hot-reload). Import `db` from there everywhere.
- **Connection: pooled** (Supabase's pgBouncer on port 6543) **with `prepare: false`** — required because pgBouncer runs in transaction mode and doesn't support prepared statements. The direct connection (port 5432) is used only by `drizzle-kit` for migrations.
- Migration workflow:
  1. Edit `db/schema.ts`
  2. `pnpm drizzle-kit generate` — produces a new SQL migration file under `drizzle/`
  3. **Review the generated SQL** before applying — Drizzle generates plain SQL you can read
  4. `pnpm drizzle-kit migrate` — applies it
- Generated migrations are checked into git. Never edit a migration after it has been applied to any environment — generate a new one instead.
- **Database access only happens server-side.** Frontend code talks to `app/api/*`, never imports `db`.
- Table names in the schema match the domain model exactly. Database uses `snake_case` (`bank_transactions`, `fee_structures`); the TypeScript export name follows the same convention. `MatchProposal` is **not** a table — it's an in-memory type only, per the domain model.
- For each table, re-export the row and insert types from `db/schema.ts`:
  ```ts
  export type Student = typeof students.$inferSelect;
  export type NewStudent = typeof students.$inferInsert;
  ```
  These are the canonical types for query results and insert payloads — never hand-write a parallel type.

## 3. Backend Architecture

API route handlers live under `app/api/<resource>/route.ts`, exporting `GET`, `POST`, etc.

**Standard route handler shape:**

```ts
// app/api/students/route.ts
export async function GET(req: Request) {
  const user = await requireUser(req);
  const params = listStudentsQuerySchema.parse(parseSearchParams(req));
  const result = await listStudents(user, params);
  return Response.json(result);
}
```

Four responsibilities, in order:
1. **Authenticate** via `requireUser()` / `requireAdmin()`.
2. **Validate** input with a Zod schema (body, query, route params).
3. **Delegate** to a service function in `features/<domain>/api.ts`.
4. **Return** typed JSON.

**Conventions:**
- **Validation: Zod, always.** Every request body, query param, and dynamic route param goes through a Zod schema. No manual `if (typeof x !== ...)` guards.
- **Errors: a single `HttpError` class** in `lib/errors.ts`, with status codes. A wrapper helper maps thrown `HttpError` to JSON responses. Service functions throw `HttpError`; route handlers don't catch — the wrapper does.
- **No business logic in route handlers.** They orchestrate. Logic lives in service functions, which are testable in isolation.
- **No N+1 queries.** Use Drizzle's `db.query.X.findMany({ with: ... })` (relational query API) for related data, or write explicit JOINs with `db.select().from(...).leftJoin(...)`.

## 4. Authentication

- **Supabase Auth** (email/password). Handles password hashing, session tokens, password reset.
- 5 users, all internal. No SSO, no OAuth, no MFA in v1.
- Sessions: HTTP-only cookies, managed by `@supabase/ssr`.
- Two roles in v1: `accountant` (default) and `admin` (manages fee structures). Stored as a column on the `User` table.

**Conventions:**
- `requireUser(req)` in `lib/auth.ts` reads the session, returns the `User`, or throws `HttpError(401)`. Every protected API route calls it as the first action.
- `requireAdmin(req)` for admin-only routes.
- The frontend uses the Supabase JS client **only** for auth flows (sign in, sign out, session reading). Never for database access.

## 5. File Handling — Bank Transaction Import

This is the highest-complexity flow in v1. Conventions matter.

- **`xlsx` (SheetJS)** for parsing uploaded Excel files. Battle-tested, handles `.xlsx` and `.xls`.
- Upload pattern: `multipart/form-data` POST to `app/api/imports/upload/route.ts`.
- **Parsing happens server-side.** Never trust the browser to parse and send structured data.
- The original uploaded file is stored in **Supabase Storage** (bucket: `bank-imports`) for audit. Reference stored as `BankTransaction.sourceFileId`.
- Parsed rows are persisted as `BankTransaction` records **before** any matching is attempted. If matching fails, the raw data is durable.
- Matching is a separate service function: takes `BankTransaction` rows, produces `MatchProposal` rows.

The parsing and matching logic lives in `features/imports/parsing/` and `features/imports/matching/` respectively, as pure functions where possible. Unit tests live next to them.

## 6. Frontend Conventions

The consistency-and-scalability requirement is enforced here. The pattern below is non-negotiable.

### Primitives in `components/ui/`

Built using **shadcn/ui** (copied into the repo via CLI, owned by us, not a runtime dependency). Underlying behavior from **Radix UI** (accessibility, focus management, keyboard nav). Variants defined with **class-variance-authority (CVA)**. Class composition via **`cn()`** (clsx + tailwind-merge), defined once in `lib/utils.ts`.

Every primitive — Button, Input, Card, Dialog, Table, Tabs, Select, Badge — follows the CVA pattern:

```tsx
const buttonVariants = cva(
  "inline-flex items-center justify-center rounded-md text-sm font-medium transition-colors focus-visible:outline-none disabled:opacity-50 disabled:pointer-events-none",
  {
    variants: {
      variant: {
        default:     "bg-primary text-primary-foreground hover:bg-primary/90",
        outline:     "border border-input bg-background hover:bg-accent",
        ghost:       "hover:bg-accent hover:text-accent-foreground",
        destructive: "bg-destructive text-destructive-foreground hover:bg-destructive/90",
      },
      size: {
        sm: "h-8 px-3",
        md: "h-10 px-4",
        lg: "h-12 px-6",
      },
    },
    defaultVariants: { variant: "default", size: "md" },
  }
);
```

### Design tokens in `app/globals.css`

All colors, radii, and core spacing constants live as CSS variables:

```css
:root {
  --primary: 222 47% 11%;
  --primary-foreground: 210 40% 98%;
  --background: 0 0% 100%;
  --foreground: 222 47% 11%;
  --muted: 210 40% 96%;
  --muted-foreground: 215 16% 47%;
  --border: 214 32% 91%;
  --destructive: 0 84% 60%;
  --destructive-foreground: 210 40% 98%;
  --radius: 0.5rem;
}
```

Tailwind reads them in `tailwind.config.ts`:

```ts
colors: {
  primary: {
    DEFAULT: "hsl(var(--primary))",
    foreground: "hsl(var(--primary-foreground))",
  },
  // ...
}
```

**Result:** changing one CSS variable rethemes the entire app.

### Hard rules

1. **No raw HTML elements in feature code.** Always `<Button>`, never `<button>`. Same for `<Input>`, `<Card>`, `<Table>`. If a primitive doesn't exist, create it in `components/ui/` first.
2. **No hardcoded colors, radii, spacing, or font sizes.** Always tokens via Tailwind classes.
3. **If a Tailwind string repeats twice, extract a component.**
4. **Page files describe layout, not styling.** A page should read like `<StudentList /> <BalanceSummary /> <ImportButton />`. Tailwind lives one layer down.
5. **Cross-feature imports go through the feature's `index.ts` barrel.** Never deep paths.
6. **No `@apply` in CSS.** Components are the abstraction layer.

## 7. Folder Structure

```
app/
  (auth)/
    login/page.tsx
  (app)/                        # protected routes; layout enforces session
    students/page.tsx           # tracking view
    imports/
      page.tsx                  # upload + recent imports list
      [id]/page.tsx             # review proposed matches, confirm
    layout.tsx
  api/
    students/route.ts
    imports/
      upload/route.ts
      [id]/confirm/route.ts
    auth/...
  globals.css                   # design tokens
  layout.tsx                    # root layout

components/
  ui/                           # primitives: Button, Input, Card, Dialog, Table, ...

features/
  students/
    components/                 # StudentTable, BalanceCell, GradeFilter, ...
    api.ts                      # service functions (listStudents, getBalance, ...)
    schemas.ts                  # Zod schemas
    types.ts
    index.ts                    # public barrel
  imports/
    components/                 # UploadDropzone, MatchReviewTable, ...
    parsing/                    # SheetJS logic, pure functions
    matching/                   # matching algorithm, pure functions
    api.ts
    schemas.ts
    types.ts
    index.ts
  auth/
    components/
    api.ts
    index.ts

lib/
  auth.ts                       # requireUser, requireAdmin
  supabase.ts                   # Supabase client (auth + storage only)
  errors.ts                     # HttpError, error handler wrapper
  env.ts                        # validated env vars (Zod)
  utils.ts                      # cn()

db/
  schema.ts                     # all table definitions (Drizzle)
  relations.ts                  # Drizzle relations (for the query API)
  index.ts                      # Drizzle client singleton
  seed.ts                       # one-time data load (students, fee structures)

drizzle/                        # generated migrations, committed to git
  0000_init.sql
  meta/

drizzle.config.ts               # drizzle-kit config (schema path, out dir, credentials)
```

**The rule:** group by *what it does*, not *what it is*. A `StudentBalanceTable` lives in `features/students/components/`, not in a global components folder. Shared primitives — Button, Input, Table — live in `components/ui/` because they're domain-agnostic.

## 8. Forms, Tables, Validation

- **Forms:** `react-hook-form` with `@hookform/resolvers/zod`. The same Zod schema validates client-side and server-side — never duplicate validation logic.
- **Tables:** `@tanstack/react-table` for the tracking view. Headless table logic (sorting, filtering, pagination); rendering uses our `<Table>` primitive.
- **Validation:** Zod is the single validation library. One `schemas.ts` per feature, shared between API route handlers and UI forms.

---

## 9. Localization

- **v1 ships in English only.** No i18n machinery in v1.
- **All user-facing strings are extracted** to a single constants file per feature (`features/<x>/strings.ts`). No string literals in JSX.
- This makes adding Mongolian later mechanical: swap the constants file for an i18n lookup, no JSX changes required.

## 10. Testing

Calibrated for a learning project that needs to ship, not a production system targeting 100% coverage.

- **Vitest** for unit tests. Highest-value targets:
  - Bank transaction parsing (given a sample Excel, returns expected rows)
  - Matching algorithm (given a transaction, proposes the right matches with the right confidence)
  - Zod schemas (round-trip validation of edge cases)
  - Service functions with non-trivial logic (charge calculation, balance computation)
- **Playwright** for one e2e per critical flow:
  - Sign in → see tracking view → search/filter
  - Sign in → upload bank file → review proposed matches → confirm → verify payments recorded
- **Skip:** UI styling tests, simple CRUD endpoints, Drizzle queries themselves. Diminishing returns.

Tests live next to source: `matching.ts` + `matching.test.ts`.

## 11. Deployment & Environment

- **Hosting:** Vercel hobby tier (free).
- **Region:** Tokyo for Vercel function execution, Tokyo for Supabase Postgres. ~80–150 ms latency from Ulaanbaatar.
- **Environments:** `development` (local), `preview` (Vercel preview deploys per branch), `production`.
- **Secrets:** Vercel env vars per environment. Never committed. Local dev uses `.env.local` (gitignored).

**Required env vars:**
```
DATABASE_URL                 # Supabase Postgres pooled connection (port 6543, pgBouncer)
DIRECT_URL                   # direct connection (port 5432, used by drizzle-kit migrate)
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY    # server-only, never exposed to client
```

A Zod schema in `lib/env.ts` validates env vars at startup and re-exports them typed. If any required var is missing, the app fails to boot — better than mysterious runtime errors.

## 12. Things explicitly excluded from v1

For clarity to future AI sessions — these are not oversights, they are decisions:

- No React Server Components for mutations, no Server Actions
- No edge runtime
- No WebSockets, no Supabase Realtime
- No i18n machinery (only string extraction, English only)
- No multi-tenancy
- No public-facing pages, no marketing site
- No analytics, no error monitoring (Sentry can come later if needed)
- No CI beyond Vercel's automatic preview deploys
- No Storybook, no component playground
- No discount/scholarship modeling (deferred per domain model)

Add any of these only when there is a concrete reason rooted in this project's needs — not because they are "standard."
